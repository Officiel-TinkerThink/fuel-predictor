# ADR 0008: Authenticate humans with server-side sessions and agents with scoped tokens

## Status

Accepted

## Context

The MVP has no accounts. Production is internet-facing and exposes an MCP endpoint, so both human
and agent callers must be identified, authorized, and audited. The plan defines three human roles
(`operator`, `manager`, `administrator`) and requires per-agent revocable credentials with scopes.

The deployment has at most five human users and no dedicated identity infrastructure. Running
Keycloak, or paying for a hosted identity provider, would cost more memory and more operator
attention than the application it protects.

## Decision

### Human authentication

Store users in PostgreSQL. Hash passwords with `hashlib.scrypt` from the standard library using a
per-user random salt and recorded cost parameters, stored in a self-describing string so parameters
can be raised later without invalidating existing hashes. Verify with `hmac.compare_digest`.

Use opaque server-side sessions, not signed client-side tokens. The session identifier is random,
stored hashed in PostgreSQL alongside its user, creation time, and expiry, and sent as a cookie
marked `HttpOnly`, `Secure`, and `SameSite=Lax`. Logout, password change, and administrative
revocation delete the session row, so access ends immediately rather than at token expiry.

Protect every browser mutation with a per-session CSRF token submitted as a hidden form field and
compared in constant time. Rate-limit login attempts per username and per source address. Expire
sessions after a fixed lifetime and after an idle period.

Authorize in the application layer, not in templates. A route declares the role it requires; the
template only decides what to draw.

### Agent authorization

Issue each MCP client its own credential with an explicit scope set, initially `fuel:predict`,
`fuel:monitor`, and `models:read`. Credentials are generated by an administrator, shown once, and
stored hashed. They are revocable individually from the administration UI, and every MCP call is
audited with caller, tool, argument summary, result status, model version, and timestamp.

The application is its own authorization server. We do not delegate to an external identity
provider, and we never forward an inbound MCP credential to another service.

## Research and adaptation

- [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
  recommends opaque, high-entropy, server-side session identifiers with idle and absolute timeouts.
  We follow it directly; this is also why we chose sessions over stateless JWTs, which cannot be
  revoked before expiry.
- [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
  lists scrypt as an acceptable memory-hard choice when Argon2id is unavailable. We take scrypt
  because it ships in the Python standard library, which keeps the production dependency surface
  and the container image smaller. The cost parameters are stored per hash so we can migrate to
  Argon2id later without a flag day.
- [MCP authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization)
  describes OAuth 2.1 resource-server behaviour for remote MCP servers. Phase 4 implements the
  bearer-token and scope checks against locally issued credentials; adopting full dynamic client
  registration is deferred until a real harness needs it.

We rejected Keycloak, Auth0, and any external identity provider: each adds either a service that
does not fit the memory envelope or an external dependency and recurring cost that five users do
not justify. We rejected stateless JWT sessions because immediate revocation is a stated
requirement.

## Consequences

Sessions and credentials require new tables and a new Alembic revision. Every existing route gains
an authorization decision, and the current unauthenticated MVP routes stop being reachable
anonymously; existing tests must establish a session.

Because the application is its own authorization server, credential rotation and lockout are
operator procedures this project must document and rehearse rather than delegate. If a future
deployment does need federated login, this decision must be superseded rather than quietly extended.
